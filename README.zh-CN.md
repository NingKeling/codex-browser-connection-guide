# Codex 浏览器连接诊断与修复

[English](README.md)

浏览器能手动上网，但 Codex 无法打开或读取网页？如果你在 Windows 上使用本地 HTTP 系统代理，可以先复制下面的提示词。其他情况可查看后面的报错表，或把[独立 AI 参考文件](AI-REFERENCE.zh-CN.md)交给自己的 AI。

本文分享的是在一套 Windows、Edge 环境中验证过的办法。相同报错也可能有其他原因。

## 一、复制修复提示词

本地 HTTP 系统代理已开启，且 Codex 出现下面任一种报错时，可以检查这一分支：

- `nodeRepl.fetch request failed`
- `Unable to load browser request-header policy`

把整段复制给 Codex，并替换报错占位符：

```text
我在 Windows 上使用 Codex，浏览器能手动上网，但 Codex 操作网页失败，报错是：[粘贴完整报错]。

请先检查浏览器工具子进程是否实际获得并使用本机当前的本地 HTTP 系统代理，不要只凭报错文字认定根因。若证据指向代理传递问题，读取当前启用的代理地址和端口，只为浏览器相关子进程补充 HTTP_PROXY、HTTPS_PROXY、NO_PROXY。

需要持久化且确需自定义用户级入口时，先在本机生成附带可审查源码的入口，再通过 CODEX_NODE_REPL_PATH 启用。按应用传入的 NODE_REPL_NODE_PATH 选择官方运行时，先确认当前版本支持这些接口，不兼容就停止这一分支。保留运行时路径与签名校验，正确且及时地转发 stdin、stdout、stderr、参数和退出码，并保留当前环境需要的其他代理排除项。

修改前记录原值和恢复办法，保留官方安装包、认证、TLS 校验、浏览器权限和现有审批边界。

在我已授权的范围和当前工具权限内执行。完成后告诉我如何重启；等我保存工作、完全退出并从原版图标重新打开 Codex 后，用正式浏览器工具实际打开公开 HTTPS 测试页、读取标题和可见正文，再仅关闭本次测试页并确认其消失，保留原有标签页。分别报告打开、读取、关闭的结果，不凭配置检查宣称修复成功。
```

**本机有效的方法：**2026 年 10 月 15 日，通过本机生成的自适应入口，为浏览器相关子进程补上当前代理。完全退出并从原版图标重新启动 Codex 后，正式 Edge 浏览器工具成功打开 HTTPS 网页、读取内容并关闭测试页。

仅设置 `CODEX_NODE_REPL_PATH` 不会自动生成入口。本文提供诊断和本机适配方法，没有现成通用安装程序。案例中的入口接口与版本有关，不代表官方承诺所有版本都支持。

扩展未安装或未启用时，先按[官方浏览器连接说明](https://learn.chatgpt.com/docs/chrome-extension#troubleshooting)完成设置。

## 二、重启后验收

保存工作，完全退出 Codex，再从平时使用的原版图标启动，发送：

```text
请用当前正式浏览器工具，在我选择的浏览器中新建临时标签页，打开一个我能手动访问、且工具允许访问的公开 HTTPS 网页。

报告实际网址、页面标题和一段可见正文，再仅关闭本次测试页，确认其已消失，保留原有标签页。

分别报告打开、读取、关闭的结果。失败时保留完整报错，指出最早卡在哪一步。调用超时后先确认测试页是否已存在，再决定是否重新创建。
```

重启后，打开、读取、关闭三项都成功，才算本轮网页验收通过。扩展侧边聊天、进程列表、入口回执或命令行 HTTP 请求成功，只能证明对应环节可用。

## 三、恢复修改前的配置

让 Codex 按本次记录，恢复用户级 `CODEX_NODE_REPL_PATH` 的原值，以及这次修复做过的其他改动。只有确认原来不存在该变量时，才移除新增项。保存工作后完全退出并重新打开应用。

如果 Codex 已无法启动，在 Windows 搜索"编辑帐户的环境变量"，按备份恢复该用户变量。仍读取到旧值时，先保存其他工作，再注销并重新登录 Windows。

## 四、其他报错与排查方向

下表用于选择下一步，不代表所有案例具有相同根因。

| 报错或现象 | 建议先做什么 | 依据与验证情况 |
| --- | --- | --- |
| 浏览器不在列表或 @ 菜单中。 | 核对当前浏览器配置文件、扩展和 Settings → Computer Use，确认显示 Manage 且开关开启。 | [官方建议](https://learn.chatgpt.com/docs/chrome-extension#troubleshooting)。 |
| 扩展已安装，连接仍失败。 | 尝试新建对话、重启浏览器和应用、检查更新；必要时通过 Computer Use 重装扩展。 | 官方建议，设置完成后仍须网页验收。 |
| `Unable to load browser request-header policy`。 | 有代理相关证据时检查工具子进程的代理环境，否则保留初始化错误继续定位。 | 本机验证过代理分支；[#45678](https://github.com/openai/codex/issues/45678)报告同类报错，但未确立根因。 |
| `Timed out waiting for Statsig values`。 | 保留初始化与网络错误，不只凭提示推断代理问题。 | 既有诊断材料中的参考方向，本机未独立验证其修复。 |
| 汇总全部浏览器时出现 `nodeRepl.fetch request failed`。 | 当前工具文档支持时，直接选择目标浏览器，再分别测试列标签和读页面。 | [他人个案有效](https://github.com/openai/codex/issues/45340#issuecomment-5658617066)，本机未验证。 |
| `js execution timed out; kernel reset, rerun your request`。 | 先确认页面是否已创建，区分标签元数据可用与页面实际可读。 | [页面已创建、读取仍超时的报告](https://github.com/openai/codex/issues/45340#issuecomment-5846770054)。 |
| 内置浏览器返回 `browsers=[]`，尚未创建标签页。 | 尝试新建对话、完全重启和检查更新，仍失败时保留初始化错误。 | [macOS 内置浏览器报告](https://github.com/openai/codex/issues/53062)，不能直接套用 Windows 入口。 |
| 只有某个网站失败，或明确提示访问受限。 | 检查站点限制并按正常流程授权；允许访问时再对比其他公开网页。 | 官方建议与对照诊断方向。 |
| 当次有效，重启或升级后失效。 | 对比前后的实际入口、代理环境和应用选定的运行时，检查配置是否被重建。 | [配置覆盖报告](https://github.com/openai/codex/issues/52956)，其重新打包应用的办法与本文方案不同。 |

仍无法解决时，在应用中运行 `/feedback`，按官方说明提供版本、完整报错、失败步骤和聊天 ID，相关日志先脱敏。

## 五、本机验证范围

- 验证环境为 Windows、Edge，以及单个、无凭据的本地回环 HTTP 系统代理。记录中的 Windows 应用包为 `OpenAI.Codex 26.1007.9446.0`，不是 About 页或 CLI 版本号。
- 本机遇到过 `nodeRepl.fetch request failed` 和 `Unable to load browser request-header policy`。
- 2026 年 10 月 15 日的历史记录确认，原版图标重启后的真实网页打开、读取、关闭均通过。
- 原入口不支持 PAC、分协议代理映射或带账号密码的代理，并要求本地系统代理保持启用。
- 原实现将 `NO_PROXY` 替换为 `localhost,127.0.0.1,::1`，不会自动合并原有排除项。为其他电脑适配时，必须考虑其环境需要的其他排除项。
- 自定义入口的小消息缓冲缺陷也曾修复，不能把它说成已证实的官方产品缺陷。
- 真实下一次官方应用升级后的兼容性尚未验证。当前运行时和模拟路径选择通过，不代表未来版本一定兼容。
